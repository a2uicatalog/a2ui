Macro Packs

A macro pack lets a model write one short macro call instead of a whole screen. The server expands that call into a tree of ordinary Basic Catalog components, so the client needs nothing new.

Catalog pack or macro pack

A catalog pack runs in the client: the host registers its components before a renderer can draw them. A macro pack runs on the server and sends ready-made components, so the client has nothing to register when those components are from the Basic Catalog.

Macro expansion is part of the official A2UI project: its Python agent SDK has a macros module, in its transformers package, with a @macro decorator and a MacroExpander class.

Two targets: the Basic Catalog and a custom catalog

Basic Catalog target (what our packs do today)

The macro call expands to Basic Catalog components: a Card, Text, and an Image that carries the drawing as an SVG, with Row and Button when the example has controls. The examples on the d3 pack page list the exact components of each. Because everything in the message is a Basic Catalog component, any renderer that supports the Basic Catalog can show it.

Custom catalog target (planned, not built)

In a custom catalog the same call would expand to our own components (atoms) in place of the Image, so the client draws the chart itself. Our d3 atoms take the same inputs as the d3 pack's macros where an atom exists. No pack emits atoms today: every message our packs send names the Basic Catalog and nothing else, and there is no demo of the custom target yet.

Our two packs

  • The d3 pack27 macros: d3-style charts plus Connect Four, a brick builder, availability and a latency ledger, each drawn as an SVG in Python.
  • The architecture packOne macro, arch_motion: an architecture diagram with a wide and a narrow view and motion that plays once.

Status
